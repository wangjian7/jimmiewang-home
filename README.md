# Jimmie 网站群 / 项目群总览

## 总览

现在这套仓库已经不再只是“双网站”结构，而是逐步长成一组分工明确的网站群与项目栈：

- `jimmiewang.com`
  履历型个人站，负责专业感、经历厚度与长期信任。
- `jimmie.wang`
  studio 主站，负责风格识别、服务表达与合作转化。
- `atlas.jimmiewang.com`
  全部项目、资源、基础设施、agents、skills 的总目录与能力注册表。
- `cardhobby stack`
  以 `cardhobby + cardhobby.ui + cronplane + cronplane.ui` 组成的业务执行面 / 控制面四仓栈。

这意味着现在的 `jimmie` 体系已经从“个人展示”扩展成一套更完整的数字工作台：

- 有负责个人品牌与对外认知的门面站
- 有负责项目与资源检索的目录站
- 有负责真实业务运行的执行栈
- 有负责调度、任务与运维的控制面

## 一、品牌入口层

### `jimmiewang.com`

定位：

- 履历型个人站
- 经历与方法论展示入口
- 长期信用与专业感承接页

它更像你的履历入口，不是拿来“卖”的，而是拿来“立”的：

- 帮助别人快速建立专业判断
- 承接个人经历、方法论与可信度
- 作为长期内容和品牌资产的沉淀位

一句话总结：

`jimmiewang.com` 负责履历、信任和长期专业形象。

### `jimmie.wang`

定位：

- studio 主站
- 服务能力展示页
- 高辨识度的合作转化入口

它更像一个有风格的业务门面，而不是传统作品集：

- 强调第一眼记忆点
- 展示审美判断与系统表达能力
- 更适合承接 freelance / studio 合作机会

一句话总结：

`jimmie.wang` 负责风格、服务表达和合作转化。

## 二、目录与中台层

### `atlas.jimmiewang.com`

定位：

- 项目目录
- 资源目录
- 能力注册表
- 网站群 / 项目群的统一索引入口

它不是对外品牌门面，而是整个 `jimmie` 体系的“总台”和“地图”：

- 汇总所有项目、agents、skills、sources、infra、artifacts
- 用 YAML 维护，再编译成静态站与 JSON API
- 既能给人看，也能给脚本、AI、内部工具消费

当前 `atlas` 已经在扮演这些角色：

- 所有项目总览：例如 `trip`、`cardhobby`、`jcron`、`llm-wiki`
- 所有资源总览：如基础设施、外部数据源、agents、skills、artifacts
- 内部检索与导航中心：帮助快速回答“这个项目在哪、跑在哪、依赖什么”
- 统一 registry：把零散信息从记忆和对话中抽出来，变成结构化目录

一句话总结：

`atlas.jimmiewang.com` 是整个网站群和项目群的目录中枢。

## 三、业务执行层

### `cardhobby stack`

`cardhobby` 现在已经不是单仓项目，而是一套完整的四仓 stack：

| 仓库 | 角色 | 默认端口 | 职责 |
|------|------|----------|------|
| `cardhobby.jimmiewang.com` | 业务执行面 API | `8820` | 抓取、入库、富化、player master、相对价、业务 API |
| `cardhobby.jimmiewang.com.ui` | 业务前端 | `3820` | 卖家、成交、分析、球员页面 |
| `cron.jimmiewang.com` | 控制面 API / worker | `8840` | 调度、入队、运行历史、手动触发 |
| `cron.jimmiewang.com.ui` | 控制面前端 | `3840` | Jobs、Runs、参数编辑、运维入口 |

这套 stack 的关键意义在于，它不只是一个网站，而是一套可持续迭代的业务系统：

- `cardhobby` 负责业务事实与业务逻辑
- `cronplane` 负责任务调度、控制与历史
- 两个 UI 分别承接业务面板与控制台
- `deploy/dev` 与 `deploy/prod` 已经开始承担四仓一键启停入口

从结构上看，这套 stack 也给后续项目打了样：

- 业务逻辑放执行面
- 调度逻辑放控制面
- UI 只消费稳定接口
- 生产与开发围绕统一端口、环境变量和启动顺序运转

一句话总结：

`cardhobby stack` 是当前最完整的一套业务执行面 + 控制面样板。

## 四、现在的整体关系

如果从更高一层看，现在的 `jimmie` 体系大致已经形成四层分工：

- 品牌层：`jimmiewang.com`、`jimmie.wang`
- 目录层：`atlas.jimmiewang.com`
- 业务层：`cardhobby` 等垂直项目
- 控制层：`cronplane` 这类跨项目调度面

它们不是重复建设，而是在逐渐形成一个完整闭环：

- 有人先通过品牌站认识你
- 再通过项目站理解你在做什么
- 再通过 `atlas` 看到整个系统的项目版图和资源版图
- 再通过业务栈与控制栈真正把项目运行起来

## 五、当前阶段判断

和最初相比，现在已经不只是“双网站阶段”，而是进入了“网站群 + 项目群 + 运行栈”阶段。

最明显的变化是：

- 个人品牌入口已经不止一个
- 项目不再是散点，而开始有统一目录
- 业务系统不再是单仓，而开始有执行面与控制面分层
- 基础信息开始从口头上下文迁移到 `atlas` 这样的结构化 registry
